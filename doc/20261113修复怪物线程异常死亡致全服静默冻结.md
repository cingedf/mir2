# 20261113修复怪物线程异常死亡致全服静默冻结

> 体检⑤（WorkLoop 容错）第一步修复：根除多线程模式下 mob 线程异常死亡 → 主线程静默冻结的致命缺陷。按「修复方法论」单独一个点闭环。

## 现象

多线程模式（`Settings.Multithreaded`）下，任一怪物后台线程（`ThreadLoop(MobThreads[j])`，j≥1）在扫描/处理对象时抛出任意异常：

1. 原实现 catch（813-818）仅记日志后**线程函数直接结束 = 该 mob 线程永久死亡**，无人重启。
2. 死线程的 `MobThreads[j].Stop` 永远不会置 true → 主线程内联 `ThreadLoop(MobThreads[0])` 的停止判定（「所有子线程 Stop==true」）永不满足 → **主线程被吞没在 ThreadLoop 内循环**。
3. 后果：主循环 WorkLoop 642-703 段（20ms 切片、地图 Process、存档门控、公告广播）全部饿死——**进程存活、不踢人、不存档、端口还在的全服静默冻结**，比有序停机更糟（无恢复手段，只能杀进程回档）。

同源问题：单只怪物的 `Process()` 异常也会炸掉整条线程（778-786 无逐对象隔离），一只坏怪即可触发上述连锁。

## 排查过程

- **ThreadLoop 全量结构核查**（Envir.cs 744-819）：`Info.Stop=false` 起手 → try 内 init（_current==null 时取 First）→ `while(Running)` 扫描（762-765 已有 Value==null 回绕防护【首轮修复遗留】）→ Id==0 时 stopping 判定（790-803）→ Id≥1 时 EndTime 到点 Stop=true 并 `Monitor.Wait` 等唤醒（805-810）→ 外层 catch。
- **停止协议引用链核查**：`MobThreads[x].Stop` 读取点仅两处——主线程 stopping 判定（795）与子线程自身等待逻辑（806/809）；唤醒方=主线程每 tick `PulseAll(_locker)`（615-640）；停机路径=`StopEnvir` 置 `EndTime=Time+9999`（1815-1817）+ `Thread.Interrupt()` → `ThreadInterruptedException` → return。**确认「线程死亡」破坏协议的唯一致命路径就是 catch 后线程函数结束**。
- **出链防护现状核查**（MapObject.cs 361-402）：Spawned 时怪物入 `MobThreads[SpawnThread].ObjectsList`（AddLast 后若 `mt._current` 无效则指到新节点）；Despawn 时若 `_current` 正指向被删节点则前移到 `Previous ?? First` 再 Remove。前轮防护完整，本次不重复处理。
- **多线程访问核查**：`_current` 只被所属线程自身与主线程（Despawn 前移、Spawned 修复）读改——改动后 `Stop=false` 复位与主线程判定为同一 bool 的常规读写（与原实现 746 行置 false 同一语义）；`ErrorThrottle` 用 `ConcurrentDictionary` 支撑 mob 线程与主线程并发记账。
- **编译期发现并修正**：`Envir.Time` 为实例属性（非静态），节流器初版误写 `Envir.Time` 报 CS0120，改为 `Envir.Main.Time` 后通过。

## 修复内容

全部集中在 `Server\MirEnvir\Envir.cs`（单文件单点，逐个完美修复）：

1. **`MobThread` 类新增 `public int ErrorCount = 0;`**：该线程累计处理异常次数（诊断用，也供后续熔断/毒对象治理参考）。纯增量字段，不影响现有协议。
2. **新增 `public static class ErrorThrottle`**（节流日志器）：`ConcurrentDictionary<string,long>` 记账，同一 key 在窗口期（默认 10 秒）内只输出一条；多线程并发通过检查时可能重复一条，良性收敛。**此为第二步主循环逐项隔离的方法论基础设施**，本次一并落地复用。
3. **`ThreadLoop` 重构为恢复式循环**（所有原语句逐字保留，仅整体缩进 +4）：
   - 外层 `while (Running)` 包裹原 try/scan 结构：异常后回到扫描起点而非结束线程；
   - **778-785 对象处理加逐对象 try/catch**：单个对象 `Process()` 异常 → `Info.ErrorCount++` + `ErrorThrottle.Notify("ThreadLoop:"+Info.Id, ...)`（沿用原 ThreadLoopError 本地化消息）→ `OperateTime = Time + 5000` 顺延该对象重试时间（防毒对象每轮扫描被连续重锤）→ 扫描继续；原 `Process()+SetOperateTime()` 成功路径逐字保留；
   - **外层 catch（原 813-818）**：`ThreadInterruptedException` 仍 `return`（停机协议不变）；其他异常 → 计数 + 节流日志 + `Info._current` 回绕 First + `Info.Stop=false` 复位 + `Thread.Sleep(1)` 防错误路径热旋 → 外层循环重新进入扫描（**线程不再死亡，静默冻结根除**）；
   - Id==0 的 stopping 判定、EndTime 等待逻辑、回绕防护全部保留原语义。

## 验证证据

- `dotnet build Server\Server.Library.csproj -c Release`：**0 警告 0 错误**（修正 `Envir.Main.Time` 后）。
- 逻辑复核：①停机路径（Interrupt→return、EndTime=9999、Stop 协议）逐字保留；②主线程内联 thread-0 的 return 路径不受外层 while 影响（802 行 return 直接退出方法）；③恢复路径不会死循环——扫描机制本身的异常源（Process/SetOperateTime）已被逐对象 catch 覆盖，剩余外层异常源（链表 First/Next、Stopwatch、Monitor.Wait）均无抛出条件，且有 Sleep(1)+节流日志双保险；④`ErrorCount`/节流器均为增量状态，无既有消费者受影响。

## 附：第二步方法论（探索结论，未实施，待批准）

主循环逐项隔离 + 熔断（WorkLoop 642-703 段），方法论如下：

- **段位隔离清单**（catch → `ErrorThrottle.Notify` → continue，全部复用本次落地的节流器）：591-612 每连接 `Process()`（lock 内逐连接 catch，坏连接不拖全服）；653-662 切片每对象（`next` 已先取，LinkedList 天然支持安全跳过）；665-666 每地图；668 DragonSystem；670 Envir.Process。**存档段（672-680）不隔离**——存档失败属数据完整性风险，保持原停机语义。
- **毒对象治理**：MapObject 增量字段 `ProcessErrorCount`；逐对象 catch 计数，连续失败超阈值（如 5 次）→ try 包裹的 `Despawn()` + 日志（防一只坏怪永久占坑刷计数）。
- **熔断兜底**（防逐项 catch 掩盖系统性错误）：WorkLoop 级错误窗口计数（复用/扩展 ErrorThrottle 记账结构），窗口内隔离 catch 次数超阈值（如 500）→ 主动走原内层 catch 的有序停机路径（踢人+存档）。
- **实施顺序**：逐段逐个闭环（每段一次编译验证），最后上熔断；每段均有独立回滚点。
- **利弊**：收益=主循环单点异常不再全服停机；代价=毒对象残留窗口（Despawn 治理兜底）+ 行为增强类改动需逐段逻辑复核（非等价收敛，风险高于第一步，故单独分步）。
