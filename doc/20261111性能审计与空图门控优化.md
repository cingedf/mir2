# 20261111性能审计与空图门控优化

## 现象

- 用户要求对服务端源码全库核查剩余性能优化点。此前已完成：闲置烧核修复（Sleep(100)，空闲 1.6→0.27 核）、内存懒分配修复（4.4→3.2GB）。
- 本轮服务端空闲 CPU 稳定在 ≈0.24 核（817 张地图每圈全量遍历的余项），内存 2981MB。

## 排查过程（全库审计，分两批）

**架构健康项（无需改动）**：

- 网络：MirConnection 收发均为 ConcurrentQueue（上限 5000/10000），批量打包+BeginSend 异步写，超限断连保护。
- 怪物多线程：MobThreads 分片 + Monitor.PulseAll 唤醒，ThreadLimit=2。
- 定时任务（Envir.Process）：daily/war/guild/conquest/rental/auction 全部时间门控，每圈成本低。
- SaveGoods/Guilds/Conquests：NeedSave 门控 + 异步写盘。

**评估后不动的项（B/C 级）**：

- SaveDB 主线程同步序列化（每 5 分钟）：当前库 ~1MB 毫秒级，无感；后台化需处理并发安全，风险>收益。
- GetPacketBytes 每包分配 2 个 MemoryStream+BinaryWriter（Shared\Packet.cs@70-103）：序列化层改动风险大，当前广播量下收益趋零。
- 战斗路径少量 LINQ（HasBuff 的 Except+Intersect 等）：量小可接受。
- BroadcastNPC 与 Broadcast 重复实现：可合并但无性能收益。

## 修复内容（A 级，仅 3 行）

`Server\MirEnvir\Map.cs` Process()（@702）开头加空图门控：

```csharp
if (Respawns.Count == 0 && Doors.Count == 0 && !Info.Lightning && !Info.Fire && ActionList.Count == 0) return;
```

- 817 张图中绝大多数无刷怪点/无门/无特效/无动作队列，此前每圈仍要走完 ProcessRespawns+Doors 扫描+特效判定+ActionList 扫描四段空转；门控后直接 return。玩家在线/多图活动时收益最明显。
- 条件覆盖全部需处理状态，无漏（ActionList 非空时不会被跳过）。

**附带修正**：审计中曾误判 `GetAllMonstersObjectsCount`（Map.cs）为死代码并删除——编译报错后发现 SMain.cs@670-691（GM 怪物列表页「怪物数量」列）有真实调用，属管理界面功能，已原样恢复。教训：删代码前需覆盖 Server.MirForms 目录全量 grep；游戏运行中改用 Envir.Objects 链表统计有并发修改风险，原实现虽 O(全图格子) 但仅手动触发，保持原样。
