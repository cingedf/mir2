# 20261113修复广播包逐连接重复序列化加惰性缓存

> 深度体检第四轮产出可选优化⑥，经后台子代理全量调用点审计确认可行后实施（用户指令：修复⑥）。

## 现象

`Packet.GetPacketBytes()`（`Shared\Packet.cs:70`）每次调用都全量序列化：MemoryStream + BinaryWriter 两段式写出（WritePacket → 可选压缩 → 拼 2 字节长度头 + 2 字节 Index + 包体）。广播路径下同一 Packet 实例通过 `Enqueue(p)` 扇出到 N 个观察者连接的 `_sendList`，每个连接的发送泵各自调用一次 `GetPacketBytes()`——同一包字节被重复生成 N 次；第四轮①修复后的「超限包留队首下次泵重试」路径也会对同一实例重复序列化。ObjectWalk/Run/Turn、S.Chat、ObjectDied 等最高频广播包在多人同图时序列化 CPU 随人数线性放大。

## 排查过程

- **全量调用点审计（后台子代理，只读）**：两轮扫描 Server\ + Shared\ 约 400 处可变变量入队点，27 处疑似「入队后修改包实例」逐处人工核读——**全部为假阳性**（互斥分支结构，赋值只发生在成功路径唯一一次入队之前，代表点 PlayerObject.cs 5199/7497/7925/14620、HeroObject.cs 623）。
- **非确定读取核查**：285 个包类的 WritePacket 对 `DateTime.Now`/`Random`/`Envir.Time` **零命中**；时间字段均在入队前算好写入 ⇒ 同一实例两次序列化结果由对象状态唯一决定，缓存字节与重算字节必然一致。
- **广播扇出核查**：Envir.Broadcast / Map.Broadcast / MapObject.Broadcast / PlayerObject.Broadcast / GuildObject.SendServerPacket 等全部广播族确认同实例扇出、序列化期间零修改；嵌套活引用包（S.TradeItem/S.PlayerInspect/S.NPCGoods 等）冻结点=现状首次序列化点，缓存语义不变。
- **本会话调用点复核**：grep 全仓 `GetPacketBytes` 仅两处调用——服务端 `MirConnection.cs:656`（TryBeginSend 泵内）、客户端 `Network.cs:670`（发送泵内），两处均**只读消费**（`data.AddRange(packetBytes)` 拷入批缓冲/发送缓冲 + `.Length` 判断，socket 发的是拷贝件，不持有包内数组，无原地改写风险）。
- **线程模型**：服务端同实例可能被多个连接的泵并发序列化——主线程 `Process()` 第 5 步驱动 + 异步 IO 线程 `SendCompleted → TryBeginSend` 驱动（MirConnection.cs 610-627），广播扇出时 N 个连接各自持锁独立出队同一实例 ⇒ 缓存发布必须原子。

## 修复内容

`Shared\Packet.cs` 三处（服务端/客户端共享定义，单文件双端生效）：

1. 新增实例字段 `private byte[] _serializedCache;`（附带注释说明扇出/重试复用与原子发布约定）。
2. `GetPacketBytes()` 头部：先查缓存 `byte[] cached = _serializedCache; if (cached != null) return cached;`——命中即零序列化零分配；未命中走**逐字保留**的原两段式序列化。
3. 尾部发布：`byte[] published = Interlocked.CompareExchange(ref _serializedCache, data, null); return published ?? data;`——并发泵下仅发布一份，CAS 失败方返回胜者已发布的数组（内容确定性与本方一致）；读取侧普通读 null 即重算（陈旧读良性，引用赋值原子无撕裂）。

明确不受益/不受影响：逐观察者定制包（GetInfoEx NameColour 每次 GetInfo() 新建实例，天然不共享缓存）；非 Observable 包（S.Chat 密语、S.NewItemInfo，`Packet.cs` Observable=false 时不扇出，仅单连接消费，缓存同样正确）。
