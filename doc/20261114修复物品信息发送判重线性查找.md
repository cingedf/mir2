# 20261114 修复物品信息发送判重线性查找

## 现象

`MirConnection.CheckItemInfo` 在向客户端下发物品资料（`S.NewItemInfo`）前的判重：

```csharp
if (SentItemInfo.Contains(info)) return false;
Enqueue(new S.NewItemInfo { Info = info });
SentItemInfo.Add(info);
```

`SentItemInfo`（`Server\MirNetwork\MirConnection.cs:204`）为 `List<ItemInfo>`，`Contains` 是 O(n) 线性比较。该列表在连接生命周期内**只增不减**——玩家见过的每种物品资料都会留在列表里（拾取、查看、任务奖励、NPC 对话链接、制造物品等每次请求各加一条）。会话越长，判重越慢；且 `CheckItemInfo` 会对连接级观察者递归扇出，每个观察者再各自 `Contains` 一遍。

## 排查过程

- 全仓 grep `SentItemInfo`：仅 3 处引用——声明（204 行）、`Contains`（3725 行）、`Add`（3733 行）。无遍历、无 `Remove`、无重赋值，与 209 行的 `SentChatItem` 用法完全同构（后者在体检第四轮已改 `readonly HashSet<UserItem>`）。
- 核查相等语义：`ItemInfo` 定义于 `Shared\Data\ItemData.cs:3`，全 Shared 目录 grep `override bool Equals` / `override int GetHashCode` 零命中 ⇒ 默认引用相等。`List<ItemInfo>.Contains` 与 `HashSet<ItemInfo>.Contains` 对同一实例判定完全一致。
- 调用点核查（23 处命中，实际运行路径 13 处）：`QuestInfo.cs:426`、`PlayerObject.cs:1047/1056/1067/7861`、`HumanObject.cs:1741`、`HeroObject.cs:293/295`、`NPCSegment.cs:1355`、`NPCScript.cs:980`（其余为注释死调用）——均为玩家请求频率，非每帧。

## 修复内容

**`Server\MirNetwork\MirConnection.cs`**：

```csharp
public readonly HashSet<ItemInfo> SentItemInfo = new HashSet<ItemInfo>(); // 体检遗留项：List.Contains O(n) → HashSet O(1)，引用相等语义不变（ItemInfo 未重写 Equals/GetHashCode）
```

- `List<ItemInfo>` → `HashSet<ItemInfo>`；`readonly` 防止运行期被误重赋值。
- **调用点零改动**：`Contains` / `Add` 两个方法名在两种容器上签名一致，3725 行与 3733 行代码无需改动。
- 判重复杂度 O(n) → O(1 平均)；内存换 CPU（仅物品资料引用）。
- 与 `SentMonsterInfo` / `SentNPCInfo` / `SentQuestInfo` / `SentRecipeInfo` 同族字段保持风格一致（那些当前只有 Add 或小表，暂不扩大改动面）。

## 验证证据

- `dotnet build Server\Server.Library.csproj -c Release`：**0 警告 0 错误**（20.53s）。
- 语义核对：`ItemInfo` 无 `Equals`/`GetHashCode` 重写 ⇒ HashSet 引用相等 ⇒ 同一 `ItemInfo` 实例重复请求仍被正确判重，不重复下发。
- 引用面核对：全仓仅 3 处引用（声明/Contains/Add），无遍历顺序依赖、无按索引访问、无序列化（该字段仅服务端连接对象持有，不参与包写出）。
