# 20261114 修复 Shader 缺失时像素着色器无判空守卫

## 现象

- 部署客户端 `Data\Shaders\` 缺 `normal.ps` 与 `magic.ps`（官方 mirfiles 补丁包同样未提供有效 shader，仅有空 grayscale.ps 与 shadow_ps.glsl）。
- `DXManager` 三个 tint 版像素着色器函数（`SetNormal` / `SetGrayscale(float,Color)` / `SetBlendMagic`）中仅 `SetBlendMagic` 自带判空守卫，前两者无守卫。
- 这三个函数当前为**未接线死代码**（全仓零调用点），故线上无实际故障；但后续特效增强（P2 打斗特效接线 tint 染色/混合）将调用它们，若届时 shader 文件缺失就会带病运行。

## 排查过程

- 全仓 grep `SetNormal|SetBlendMagic|SetGrayscale`：tint 版三函数零调用点；`SetGrayscale(bool)` 有 6 处调用（MirImageControl L183/L191、GameScene L11348/L11352 死亡灰屏、NPCDialogs L3598/L3606、PlayerObject L5646、MonsterObject L5709、MapObject L434）。
- 逐行核对 `SetGrayscale(bool)`（DXManager.cs L228-244）：`GrayScalePixelShader == null` 时，`Device.PixelShader` 通常为 null，`null == null` 提前返回；即便残留其他 shader，`Device.PixelShader = null` 是 SlimDX 合法解绑操作。**不会崩溃**，但语义上是"解绑当前 shader"而非"无操作"，行为不干净。
- 核对 `LoadPixelsShaders`（L97-118）：三个 .ps 均为 `File.Exists` 容错加载，缺文件不影响启动。
- 结论修正：**不存在崩溃风险**（此前"SetNormal 无守卫有崩溃风险"的判断过重）。真实问题 = tint 版函数无守卫的死代码 + `SetGrayscale(bool)` 缺文件时解绑语义不干净。按防御性增强处理。

## 修复内容

仅改 `Client\MirGraphics\DXManager.cs`，3 处，逻辑核心逐字保留，只加短路条件：

1. `SetNormal(float, Color)`（原 L418）：
   - `if (Device.PixelShader == NormalPixelShader)` → `if (NormalPixelShader == null || Device.PixelShader == NormalPixelShader)`
   - 与 `SetBlendMagic` 既有守卫模式完全同型。
2. `SetGrayscale(float, Color)`（原 L430）：
   - 同型：`if (GrayScalePixelShader == null || Device.PixelShader == GrayScalePixelShader)`
3. `SetGrayscale(bool)`（原 L228）true 分支：
   - 在原 `if (Device.PixelShader == GrayScalePixelShader) return;` 之前加 `if (GrayScalePixelShader == null) return;`
   - 缺文件时保持当前渲染状态不动；`GrayScale` 状态标志仍照常记录，行为对调用方无感。

## 验证证据

- `dotnet build Client\Client.csproj`：**0 错误**（18.1s）。仅存量警告 MSB3277（WindowsBase 4.0/5.0 版本冲突，来自 WebView2 依赖，与本次改动无关）。
- 行为复核：有 shader 文件时，短路顺序为先判 null 再判相等，原相等短路路径不受影响；无 shader 文件时三个函数直接返回、不触碰 Device 状态（修复前 SetGrayscale(bool) 会解绑当前 shader）。

## 回滚方法

- `git revert` 本次提交即可；
- 或手工将三处新增的 `XxxPixelShader == null` 短路条件删除，还原为原判断。
