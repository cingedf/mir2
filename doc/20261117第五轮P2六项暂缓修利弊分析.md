# 20261117第五轮P2六项暂缓修利弊分析

## 背景

第五轮深度审计（网络底层 / 客户端非渲染 / NPC脚本引擎 / 社交系统 / 存档DB 五个新维度）共登记 29 项 P2。按「能修的修了」原则，**23 项已完成修复并闭环**（网络4 + 脚本7 + 社交存档5 + 客户端7，分四批 commit f9a78e1 / 295c4e9 / f1a31d4 / 6eef128）。本文档记录**剩余 6 项经评估暂不修改**的利弊分析——这些项并非无害，而是「修复本身的改动风险 > 缺陷带来的收益」，属于需要架构级改造或会改变既有语义的项，留待专门窗口处理。

## 一、心跳保活状态机失效（网络 MirConnection.cs）

- **现象**：`_keepAlivePending` 置 true 后不再发新心跳且标志从不复位；任意收包刷新 `TimeOutTime` 与实际心跳解耦 → 心跳保活事实上失效。
- **修的收益**：理论上有准确的心跳超时检测，可识别「假在线」连接。
- **修的风险（为何不动）**：正常玩家走 / 打怪每帧都有包，`TimeOutTime` 持续刷新，连接判定**实际并未失效**（靠收包保活）。一旦把 `_keepAlivePending && 超时` 纳入断线判定，反而可能在玩家短时间不操作（挂机站桩、看 NPC 面板、过场）时**误踢在线玩家**，并引入 token 窗口等新状态变量——收益（识别假在线）远小于风险（误踢真实玩家）。
- **结论**：保留现状。真正需要时（如出现连接泄漏导致 slot 占满）再做完整状态机重写+压测，不在此批做局部补丁。

## 二、跨线程统计字段无锁（网络 MirConnection.cs）

- **现象**：`_receiveCount` / `_sendCount` 等统计字段 `long` 在收包线程写、健康统计读（:790/851-863），无 volatile/Interlocked；`_sendQueueCount` 增减分别在两把锁内（:695-708 vs :641-675）存在偏差。
- **修的收益**：统计数据精确一点。
- **修的风险（为何不动）**：这些字段仅用于**健康统计显示**（CMain.cs:484 的 CLC 计数），不参与任何业务逻辑/权限/经济判定；数值偏差不影响游戏行为。64 位运行时对对齐 long 的读写本身原子，最坏是显示数字略有出入。加 volatile/Interlocked 的维护成本（多处改动+锁粒度调整）与收益不成比例。
- **结论**：登记不修。若未来做监控告警依赖这些数字，再统一改为 Interlocked。

## 三、补丁器并发 P_Concurrency 无效（客户端 AMain.cs）

- **现象**：配置宣称 P_Concurrency 并发下载，实际 `DownloadFile` 串行 + `task.Result` 递归清空队列（AMain.cs:84/104-118/338），配置无效。
- **修的收益**：多文件更新时下载更快。
- **修的风险（为何不动）**：改成真并发需处理共享下载目录文件竞争、写入同一进度/错误集合的加锁、断点续传与失败回滚——是**下载子系统架构改造**，远超 P2 范围。私服客户端更新频率极低（一版本一次），串行下载的耗时可接受。本批已修补丁器「异常中断 + CPU 忙等」（Client\Program.cs），解决了实际痛点；并发提速无实际痛点。
- **结论**：登记不修。若未来补丁体积增至数百 MB 且用户明显抱怨更新慢，再立项并发改造。

## 四、LoadMines 读取副作用污染 ini（脚本 Settings.cs:1277-1303）

- **现象**：读取挖矿配置时顺带写回 ini（读取方法有写副作用），可能改变配置格式/覆盖手写内容。
- **修的收益**：读取纯函数化，不污染用户配置。
- **修的风险（为何不动）**：该副作用可能承担「旧格式配置自动升级/自愈」的隐含职责——直接改成纯读取会让依赖它的老配置不再被升级。正确修法需先梳理所有配置文件的版本演进与默认值策略，把「自愈」逻辑显式化到独立的迁移入口，属**配置系统改造**。收益（不写回配置）低，风险（破坏老配置兼容）高。
- **结论**：登记不修。计划在未来配置版本统一迁移时一并处理。

## 五、NeedSave 标记早清（存档 Envir.cs）

- **现象**：存盘开始即置 `NeedSave = false`，若存盘过程中对象又被修改，新变更在下个存盘周期前可能被覆盖丢失。
- **修的收益**：理论上消除存盘窗口内的变更丢失。
- **修的风险（为何不动）**：正确修法需改为「写盘成功后才清标记」，但存盘是「先清全部标记 → 异步批量写 → 成功回调」的流程，改成成功后清必须处理**存盘进行中又发生的新变更**（标记被重新置位 → 需要下一轮再存），涉及存盘时序语义重构与并发竞态。风险窗口极小（单主循环串行，存盘周期内业务变更需恰好命中同一对象），且本批已加「写盘失败时 NeedSave 复位」，覆盖了最致命的失败丢档路径。
- **结论**：登记不修。本批的失败复位已覆盖主要风险；时序重构留待存盘子系统整体升级。

## 六、归档多文件恢复（存档 Envir.cs .bak/.o/.n）

- **现象**：存档替换产生 `.bak`/`.o` 等多份归档，异常组合（主档损坏 + 备份也损坏 + 临时文件残留）下的恢复逻辑未覆盖所有排列。
- **修的收益**：极端情况下多一层恢复保障。
- **修的风险（为何不动）**：覆盖所有异常组合需要系统的故障注入测试（主档截断/备份缺失/临时文件半写等 N 种排列），且「归档恢复」本身依赖人工判断哪份是最新的有效档——自动化恢复可能选错版本反而覆盖较新的活档。此前存档 P0 批已实现**原子替换**（活档始终完整，写坏只发生在临时文件，主档不会被截断），从源头消除了「主档损坏需靠归档恢复」的场景。
- **结论**：登记不修。原子替换已保证活档完整性，归档恢复的边际价值很低；若要做需配套故障注入测试套件，单独立项。

## 总结

| 项 | 不修核心理由 |
|---|---|
| 心跳保活状态机 | 收包保活实际未失效，改判定有误踢在线玩家风险 |
| 统计字段无锁 | 仅健康显示，不参与业务，加锁收益/成本不成比例 |
| 补丁并发 P_Concurrency | 下载子系统架构改造，更新频率低无实际痛点 |
| LoadMines 读副作用 | 可能承担配置自愈职责，纯函数化需先梳理配置迁移 |
| NeedSave 标记早清 | 存盘时序重构，本批失败复位已覆盖主要风险 |
| 归档多文件恢复 | 原子替换已保证活档完整，自动化恢复可能选错版本 |

六项均已在 `doc/20261117第五轮深度审计P2遗留项登记.md` 与本文档登记。原则：**低风险高收益的 23 项已全部修复闭环；高风险低收益或需架构改造的 6 项保留现状并记录决策依据**，符合「修完不影响稳定性、不修不带出新问题」的审计收敛标准。
