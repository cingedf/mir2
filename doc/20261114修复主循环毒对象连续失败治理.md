# 20261114修复主循环毒对象连续失败治理

> ⑤容错加固第二步第 6 段（毒对象治理）。前置依赖：第 1 段切片隔离（36b1b84）、怪物线程恢复式容错（aba3b12）、第 2-5 段（每地图 e909487 / 龙系统 d5e8bc5 / 全局系统 a24da0d / 每连接 2f3f556）。用户指令「继续」后按既定方法论实施。

## 现象

逐对象隔离落地后，单个对象 Process 抛异常不再炸全服——但异常对象会被**无限顺延重试**（OperateTime = Time + 5000），形成「毒对象」：每 5 秒重试一次、每次都炸、每次都刷一条节流日志，永不退场：

1. **无退场机制**：竞态 NRE、数据边界错误等偶发异常对象与永久性损坏对象（数据腐烂、状态机死锁）无差别对待，后者永远留在场上反复失败。
2. **日志噪声**：单个毒对象每 5 秒一条日志，长期运行刷屏。
3. **玩家特殊性**：PlayerObject 无 Despawn override（基类 Despawn 仅清 ActionList/Pets + 摘链，不处理连接、装备、行会、配偶等玩家态），对玩家直接 Despawn 会造成「连接活着、对象消失」的半死状态——玩家的正确退场是走正常断线流程踢线，而非 Despawn。

## 排查过程

- **Despawn 全家福核查**：MapObject.Despawn（386-410）要求 Node!=null 否则抛 InvalidOperationException；override 清单：MonsterObject:3813（SlaveList.Clear+base）、HeroObject:219（Envir.Heroes.Remove + Node!=null 才 CurrentMap.RemoveObject + Buff 清理 + base）、SpellObject:820、DecoObject:157、门/墙等。确认：Hero/怪物/法术等均有安全 override；PlayerObject 确认无 override ⇒ 走踢线出口。
- **踢线出口核查**：MirConnection.Disconnect(byte reason)（MirConnection.cs:1563）——lock(_connectionLock) + 状态幂等检查 + 置 Disconnected，走正常异步断线（StopGame→玩家清理→存档）；PlayerObject.Connection 属性存在，null 安全（`?.`）。
- **钩子点定位**：切片隔离 catch（Envir.cs ~709，key "WorkLoopSlice:"）、ThreadLoop 逐对象 catch（~884，key "ThreadLoop:" + Info.Id）——两处是全部逐对象隔离点，也是毒对象治理的天然挂点；ThreadLoop 外层 catch（线程级恢复）不动。
- **可达性核查**：MapObject.cs 已有 `using Server.MirEnvir;`（第 3 行）+ `protected static MessageQueue` 属性 ⇒ ErrorThrottle/MessageQueue 直接可用，无需新增 using。

## 修复内容

1. **`Server\MirObjects\MapObject.cs`**：
   - 新增字段 `public int ProcessErrorCount;`（OperateDelay 之后，注释标明「成功一次即清零」）。
   - Despawn() 后新增 `public void HandleProcessError(Exception ex, string source)`：
     - `ProcessErrorCount++` → `ErrorThrottle.Notify("ProcessError:" + ObjectID, ...)` 节流日志（含 source/Race/累计次数）；
     - `count > 5` 时按 Race 分流：**Player** → 日志 + `(this as PlayerObject)?.Connection?.Disconnect(3)`（踢线走正常断线流程）；**其余** → 日志 + `Node != null` 时 `Despawn()`（Hero/怪物等 override 已确认安全）；
     - 整个清理段包 try/catch：清理自身异常 → `ErrorThrottle.Notify("ProcessErrorCleanup:" + ObjectID)` 吞掉——**catch 内代码绝不能再抛**；
     - 方法头部注释标明调用契约（仅由隔离 catch 调用、自身不得抛出）。
2. **`Server\MirEnvir\Envir.cs`** 两处隔离 catch 同构改造：
   - 切片段：`ErrorThrottle.Notify("WorkLoopSlice:"...)` → `sliceObj.HandleProcessError(ex, "主循环切片")`；保留 `OperateTime = Time + 5000` 顺延；**try 成功路径加 `sliceObj.ProcessErrorCount = 0;`**（连续失败语义：成功一次即清零，防止对象累计「终身 5 次偶发错误」被误处置）。
   - ThreadLoop 段：同构（source "怪物线程"）；保留 `Info.ErrorCount++`（线程级统计）与 OperateTime 顺延；成功路径加 `ProcessErrorCount = 0`。原 `ErrorThrottle.Notify("ThreadLoop:"...)` 本地化日志由 HandleProcessError 的结构化日志取代（含对象 ID/Race/次数，信息量只增不减）。

## 验证证据

- `dotnet build Server\Server.Library.csproj -c Release`：**0 警告 0 错误**。
- 逻辑复核：
  - 阈值语义：连续 6 次失败（>5）才处置；期间每次失败 OperateTime +5000，即最快 25 秒退场，期间日志至多 2 条（10s 窗口节流）。
  - 玩家误踢防线：成功一次即清零 ⇒ 仅「连续」失败才累计；处置走 Disconnect 正常流程（触发存档/StopGame），非硬杀。
  - 并发安全：切片 catch 内 sliceObj 为提前捕获引用；Disconnect/Despawn 内部各自有锁与幂等检查；HandleProcessError 只被主线程（切片）或对应 mob 线程（ThreadLoop）调用，同类对象不会双线程同时调用（主线程切片只处理非怪物/宠物，怪物归 mob 线程）。
  - Node==null 的对象 Despawn 调用被 `Node != null` 门控，不会抛 InvalidOperationException。
