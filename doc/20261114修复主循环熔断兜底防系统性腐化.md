# 20261114修复主循环熔断兜底防系统性腐化

> ⑤容错加固第二步第 7 段（收官段）。用户 @125@ 批准「继续第7段」。前 6 段将主循环各热段改为逐项隔离（catch→节流日志→continue），本段补上防滥用兜底：隔离不是无底洞，系统性腐化必须升级为有序停机。

## 现象

前 6 段落地后存在一个理论漏洞：若出现**系统性腐化**（如某次改动导致批量对象/全部地图同时损坏、数据文件整体异常），逐段隔离会把异常无限吞掉——每个周期数百次 catch + 节流日志，服务器「活着」但功能全面失灵，玩家处于半残状态且没有任何停机信号。隔离容错的设计前提是「单点偶发异常」，需要一道兜底把「批量持续失败」升级回原有的有序停机语义（踢全服+存档），保护数据与可运维性。

## 排查过程

- 重读 6 处隔离 catch 现场（前段编辑后行号漂移）：切片 ~708、每连接 ~634、状态连接 ~650、每地图 ~731、龙系统 ~745、全局系统 ~757（均为 `ErrorThrottle.Notify` 或 `HandleProcessError` 首行）；内层致命 catch 现位于 794-810（踢全服 SendDisconnect(3) + StackTrace 行号日志），其后 812-816 StopNetwork+StopEnvir+SaveAccounts+SaveGuilds(true)+SaveConquests(true) 有序停机，逐字未动。
- 方案比选：**A. 停机逻辑抽方法被熔断调用**——需把 794-816 的停机体复制/抽公共方法，改动致命路径本体，违背「逻辑核心逐字保留」纪律，弃。**B. 计数后主动 throw new Exception**——StackTrace 行号指向熔断器自身而非真实病灶，排障信息劣化，弃。**C（选定）. catch 内 `if (熔断) throw;` 重抛原异常**——原异常携带完整堆栈传播到内层 catch，行号指向真实病灶，停机路径零改动；语义=「把原异常归还给原有的致命处理」。
- 范围界定：仅主线程 WorkLoop 六处隔离 catch（切片/地图/龙/全局/连接/状态连接）；mob 线程 ThreadLoop 不纳入——已有线程级 ErrorCount 统计，且 mob 线程异常不经过内层 catch（跨线程 throw 无意义），维持既有恢复式语义。
- 并发模型：六处全部在主线程 WorkLoop 单线程内执行；ErrorCircuitBreaker 仍用 Interlocked 实现窗口滚动，防未来误用，竞态语义良性（少记/多记均不破坏保护性降级）。
- 锁内重抛安全性：连接/状态连接两处 catch 位于 `lock` 语句块内，rethrow 传播出 lock 块时监视器由编译器生成的 finally 自动释放，无死锁窗口。

## 修复内容

1. **`Server\MirEnvir\Envir.cs` 新增 `ErrorCircuitBreaker` 静态类**（紧随 ErrorThrottle 之后）：
   - 阈值 `Threshold = 500`，滑动窗口 `WindowMs = 60000`（1 分钟）；
   - `Record()`：窗口滚动用 `Interlocked.CompareExchange(ref _windowStart, now, windowStart)` 抢占（输家沿用旧窗口计数，少记良性）+ `Interlocked.Increment(ref _count)`；窗口内累计 ≤500 返回 false；超阈值时先经 `ErrorThrottle.Notify("CircuitBreakerTripped", ...)` 输出一条熔断日志（防刷屏），然后返回 true。
2. **六处隔离 catch 统一首行**：`if (ErrorCircuitBreaker.Record()) throw; // 熔断：送回内层致命 catch 有序停机`——切片段插在 `HandleProcessError` 之前（熔断时毒对象计数/顺延不再执行，停机优先）；其余五处插在 `ErrorThrottle.Notify` 之前。原异常原样重抛（`throw;` 保留堆栈），由内层 catch 走原封不动的踢全服+存档停机，StackTrace 指向真实病灶。
3. **语义矩阵**：单点偶发（正常故障率）→ 隔离+节流日志+毒对象治理，服务不中断；批量腐化（1 分钟内隔离 catch 超 500 次，≈每秒 8 次）→ 熔断 → 有序停机（踢人+存档），可运维可排查。
