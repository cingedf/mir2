# 20261110修复主循环空闲烧核

## 现象

- 服务端**无人在线**时持续烧 CPU：~1.5–1.6 核（4 核机器烧掉 40%）。
- 内存空闲时维持 ~4.5GB（旧版基线同数据 ~963MB，差异未归因，见“已知残留”）。
- 系统总内存 8GB 被压满（空闲仅 0.2GB），用户卡感来源。

## 排查过程（全部实测）

1. **DATAS 实验证伪（A/B）**：.NET8 开启 ServerGC + DynamicAdaptationMode=1（csproj 两行）后，Private 3 分钟仅 4602→4530MB，空闲 CPU 反而实测 277s/180s≈1.5 核；关闭 DATAS 后 288s/180s≈1.6 核。两次结果一致 → DATAS 与内存不缩、烧核都无因果，回滚。
2. **Defender(MsMpEng) 实测 0 CPU**，杀软洗清。
3. **线程快照**：一线程 Running 烧满 ~1 核，另有线程 Wait 循环烧 ~0.5 核 → 主循环本身在尾转。
4. **真凶定位**：`Envir.cs` 主游戏循环 `while(Running)`（@578-704）**无任何 Sleep/闲置门**——每圈固定执行：817 张地图的 `Process()` + 20ms 滑窗扫 Objects 链表 + （Multithreaded 时）PulseAll 呼醒 worker + 全局 Process/ProcessRespawns。作者原写法第 702 行有闲置节流但被注释：`// if (Players.Count == 0) Thread.Sleep(1); // GC.Collect();`。无人在线 = 循环照跑满速 = 烧核。
5. **假读数教训**：上午某次“空闲 60s CPU=0”读数为**取样假象**——当时系统内存枯竭（空闲 0.2GB）进程被页出，勿以单点读数下结论，需连续采样。

## 修复内容

`Server/MirEnvir/Envir.cs` 主循环尾（@702）恢复并加深作者的闲置节流，仅一行：

```csharp
if (Players.Count == 0) Thread.Sleep(100);
```

- 触发条件 = 无人在线；玩家进来条件立即失效，循环满速恢复（登录入口最坏多等 100ms，无感）。
- 选 100ms：Sleep(1) 实测仍烧 0.92 核（817 张地图每圈都趟，循环频率高）、Sleep(20) 为 0.645 核、Sleep(100) 为 0.28 核；再大收益递减。
- **有意不恢复配套的 `GC.Collect()`**并实测否决：空闲每次全堆收集在 4.5GB 活堆上烧 60ms+，实测空闲 CPU 升至 0.97 核且内存纹丝不动（数据全为活对象，GC 无物可收）。该行是作者为旧数据量时代所写，现数据规模下为负优化。

## 验证证据

| 版本 | 空闲 CPU（60s 采样差） | 结论 |
| --- | --- | --- |
| 无节流（原始） | 288s/180s ≈ 1.6 核 | 烧核 |
| DATAS 开 | ≈1.5 核 / 内存不缩 | 证伪，回滚 |
| Sleep(1) | 55.5s/60s ≈ 0.92 核 | 有效不足 |
| Sleep(20) | 38.7s/60s ≈ 0.645 核 | 中间档 |
| Sleep(100)（终版） | **16.3s/60s ≈ 0.27 核** | 达标，降 83% |

- 终版启动：7000 端口 LISTENING、无人在线空闲 0.27 核、Private=4522MB 稳定（含 GC.Collect 对照实验后不变）。
- 内存结论：4.5GB 为**活数据**（显式 GC 也收不回），非泄漏（60s 零增长），GC 配置非成因（DATAS 证伪）。

## 已知残留（不在本轮范围）

- **4.5GB vs 旧版 963MB 的内存差**未归因（同为 .NET8 运行时、DB 仅差 26 字节）——如需深挖，另行使用 dotnet-counters/gcdump 专项分析。
- `Logs\Spawn\` 无人在线仍每分钟成片记录“怪物刷新失败 地图452/453 怪物 index 400-412”（跌落失败重试有 1 分钟冷却日志门，非 CPU/内存元凶）——刷怪失败根因为独立后续问题。
