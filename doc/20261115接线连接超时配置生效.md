# 20261115接线连接超时配置生效

> 低优审计报告（四维度复核）维度①死字段处置之一：`Settings.TimeOut` 声明+Load+Save+配置框齐全但服务端逻辑零消费（网络层硬编码 60000ms），管理员改配置框无效。按审计建议接线。

## 现象

- server.exe「配置→连接设置」有 TimeOut 输入框（ConfigForm），改完保存写 Setup.ini，但连接超时行为从不变化——`MirConnection.cs:190` 硬编码 `private const long ConnectionTimeout = 60000;`，`Settings.TimeOut`（默认 10000）全仓除 Settings/ConfigForm 外零消费。管理员可感知的"假配置"。

## 排查过程

- 审计子代理四路取证：TimeOut 声明 Settings.cs:68（Network 组）+Load :400+Save :695+ConfigForm.cs:19/:90-91 绑定；消费点硬编码现场 MirConnection.cs:190（const 60000）+:271（连接建立 `TimeOutTime = Envir.Time + ConnectionTimeout`）+:385（收包刷新）+:786-792（判定 Disconnect(21)）。
- 单位勘定：Settings.TimeOut 是 ushort，原默认 10000（意图 10 秒）；现行硬编码 60000ms（60 秒）——若直接接 10000 会把全服超时从 60s 收紧到 10s（行为变化，违背不带出新问题）。拍板：**接线 + 默认值改 60000 与原硬编码一致**（行为零变化、配置框从此生效、已有用户 Setup.ini 里存的旧值 10000 会在下次保存时被自然更新）。
- `static readonly long`（非 const）——Settings.TimeOut 是静态字段，const 要求编译期常量，且 readonly 保持单次初始化语义（Settings 加载发生在任何连接创建之前：SMain 启动序 Settings.Load → Envir.Start → 网络层）。

## 修复内容

1. **`Server\MirNetwork\MirConnection.cs:190`**：`private const long ConnectionTimeout = 60000;` → `private static readonly long ConnectionTimeout = Settings.TimeOut;`（注释说明审计接线与单位/默认值对齐；:271/:385 两处消费点零改动——引用同一符号）。
2. **`Server\Settings.cs:68`**：`TimeOut = 10000` → `TimeOut = 60000`（默认值对齐原硬编码，首次生成 ini 或读旧 ini 缺键时取 60000）。

## 验证证据

- `dotnet build Server\Server.Library.csproj -c Release`：**0 警告 0 错误**（22.63s）。
- 行为零变化：默认配置下 ConnectionTimeout=60000 与原硬编码一致；超时判定（Disconnect(21)）/KeepAlive/重连逻辑全部未动。
- 上线验证：改配置框 TimeOut 为 30000 → 重启服 → 断网 30 秒后连接被踢（Disconnect 21 日志）；回 60000 恢复。

## 回滚方法

```
git revert <本提交>
```

或手工还原两处（MirConnection.cs:190 恢复 const 60000；Settings.cs:68 恢复 10000）。
