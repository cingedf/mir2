# 20261116Map编辑器设备丢失与小地图拖拽及批量导出修复

## 现象

用户实测六项新功能版本后报告 5 点：

1+2. **两次同样报错崩溃**：`SlimDX.Direct3D9.Direct3D9Exception: D3DERR_DEVICELOST (-2005530520)`，at `SlimDX Device.Present()` → `Map_Editor.Main.MapPanel_Resize`（Main.cs L652）← `Control.OnSizeChanged/WmWindowPosChanged`。即拖动主分割条/窗口布局变化触发 MapPanel Resize 时，设备丢失状态下 `Device.Clear+Present` 抛异常。
3. **浮动小地图不能拖大拖小**：面板边缘按左键无反应（实际有边缘拖拽实现但拖拽公式有 bug，用户感觉"拖不动"）。
4. **批量导出小地图行为不对**：点击菜单后表现异常/未开地图时报错，预期=选目录循环导出全部 .map。
5. **性能与内存核查**：先出可行性方案（不动手）。

## 排查与修复

### 1+2 DeviceLost（已修）

- **根因**：Render 主循环（Main.cs L300-354）有 `catch (Direct3D9Exception) → DeviceLost` 容错，但 `MapPanel_Resize`（L646-659）没有——拖分割条改变 MapPanel 尺寸 → SizeChanged → Resize 处理器里 `Device.Clear+Present` 在设备丢失时直接抛异常崩溃。
- **修复**：MapPanel_Resize 包 try-catch：`Device.Clear+Present` 移入 try，`catch (Direct3D9Exception)` 静默（中文注释说明与 Render 主循环容错方式一致：设备丢失时交由 ResetDevice 重建设备）；`DXManager.ResetDevice()` 在 catch 外始终执行。

### 3 浮动小地图拖拽（已修，两处 bug）

- **真 bug 1（拖拽公式）**：原 Move 逻辑 `miniMapDragStartSize.Width + (e.X - miniMapDragStartSize.Width)` 中 e.X 是面板内坐标，会随 Size 变化漂移——等价于 Size 只按当前 e.X 直接钳位跳动，实际拖不动。
- **修复**：MouseDown 时记录起点鼠标屏幕坐标 `miniMapDragStartMouse = Cursor.Position`；MouseMove 中 `dx = Cursor.Position.X - startMouse.X`、`newW = Max(120, startW+dx)`（高度同理 Max(100,...)）——按真实鼠标位移计算，拖动顺滑。
- **真 bug 2（命中区太小/不可发现）**：命中区从边缘 8px 扩到 **12px**；新增**右下角拖拽把手**（"◢" 18x18 Label，Anchor=Bottom|Right，Gainsboro，SizeNWSE 光标），挂同一套拖拽事件，肉眼可见易抓取。

### 4 批量导出（已修，彻底解耦）

- **根因**：RenderMiniMapBitmap() 内部直接读全局字段 M2CellInfo/mapWidth/mapHeight；批量导出靠临时替换/恢复全局字段实现——与浮动小地图面板（RefreshMiniMapPanel 同样读全局字段）竞争，且依赖"已开地图"，逻辑脆弱。
- **修复**：
  - `RenderMiniMapBitmap()` 参数化为 `RenderMiniMapBitmap(CellInfo[,] cells, int width, int height)`（三层绘制逻辑不变，只换数据来源）；调用点 createMiniMap 与 RefreshMiniMapPanel 传 `(M2CellInfo, mapWidth, mapHeight)`。
  - `menuBatchExportMiniMaps_Click` 重写：循环内 `MapReader reader = new MapReader(file)` 后直接 `RenderMiniMapBitmap(reader.MapCells, reader.Width, reader.Height)`，**完全不碰全局字段**；前置检查从 M2CellInfo==null 改为 `Libraries.Loaded`（图库未加载才拦）——**未打开地图也能批量导出**。
  - finally 只恢复 Cursor+刷新浮动面板。

### 5 性能与内存核查方案（只出方案，未动手）

| # | 风险点 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| P1 | RenderMiniMapBitmap 每格 try-catch + 每次绘制 `Graphics.FromImage` | 三层循环内每格新建 Graphics（700x700 图 ≈150 万次） | Graphics 提到循环外创建一次复用；try-catch 移到索引访问处仅包裹 CheckImage/取图 | 高（收益大改动小） |
| P2 | 批量导出大图内存峰值 | `new Bitmap(mapWidth*12, mapHeight*8)`：700x700 图 = 8400x5600x4B ≈ **188MB** 中间位图，逐张创建释放 | 改为直接按 1/8 尺寸渲染（步进 8 格采样一次），或行缓冲分段；峰值可降到 ~3MB | 高（大地图必备） |
| P3 | CheckImage 懒加载重复索引 | 每格 3 层都查 `Images[n]`，已缓存图不重载（OK）；异常吞嗤在循环内成本高 | 与 P1 一并处理即可；不需要预加载 | 低 |
| P4 | 批量导出无进度反馈 | 大目录导出时 UI 冻结无提示 | 加 ProgressBar/状态栏计数（每张 Update）或 BackgroundWorker | 中 |
| P5 | 图库内存占用 | Tiles.Lib 177,966 张图懒加载，用多少占多少；浮动面板/预览缩略图均有缓存 | 现状健康；如需可加"释放内存"按钮对 MImage.Image 过期清理（已有 FreeMemory 菜单） | 低 |
| P6 | SlimDX 设备内存 | ResetDevice 重建设备时有全量纹理重建成本 | 已有 DeviceLost 容错链路，无需改 | — |

**建议实施顺序**：P1+P2 一起做（RenderMiniMapBitmap 重构，一次改动同时优化单图导出/浮动面板/批量导出三条链路），P4 随后。预计各 0.5 天内，零行为变化（产出 PNG 像素一致或按 P2 采样率变化需说明）。

## 性能优化实施（2026-11-16 追加，用户令：前三个风险点全部处理+全面审阅其他优化）

### 已实施

**①② 渲染与内存峰值重构（RenderMiniMapBitmap，Main.cs ~L5973-6118）**
- 直接按 1/8 目标尺寸渲染：中间位图从 8 倍尺寸（700x700 地图 8400x5600x4B≈**188MB**）降到目标尺寸（~3MB）。
- Back 层步进改 8 格采样一次（原 2 格采样+缩 1/8 等效观感）；Middle/Front 矩形换算到 1/8 坐标系。
- **Graphics 单次创建循环外复用 + Bilinear 插值**（原每格 Graphics.FromImage 约 150 万次/700x700 图）。
- try-catch 只包图库取图；Middle/Front 加 mi.Image 宽高≥4 守护；mi 判空统一为 `mi.Image != null`（绘制只画 Image）。

**③ 批量导出进度窗（menuBatchExportMiniMaps_Click）**
- 420x130 无边框置顶进度窗：Label（当前序号+文件名）+ ProgressBar；每张 `Application.DoEvents()` 保响应；finally 关窗+恢复光标+刷新浮动面板。

**④ 窗体标题降频（UpdateEnviroment L263-285）**
- 原：每帧 `Text = string.Format("FPS: ...")` → 每帧 WM_SETTEXT+标题栏重绘（纯开销）。
- 改：FPS 每秒统计一次，仅值变化时更新标题（其余帧只 `_fps++`）。

**⑤ Draw 矩阵赋值削减（Main.cs L521-539）**
- 主渲染 Draw（每格每帧调用）删除尾部 `Sprite.Transform = Matrix.Identity`——下一次 Draw 开头必先设 Scaling，该 Identity 无实际作用，每格省一次矩阵赋值。
- DrawBlend（透明混合叠加）保留 Identity（混合后需还原默认变换，且不在每格高频路径）。

### 审阅结论（不实施，仅记录）

- **空闲全速重绘架构**：Application.Idle while 循环每帧全场景重绘是原设计（动画标签/选中闪烁依赖连续帧），PresentInterval.One 已垂直同步限帧；加 dirty 标记理论可省无变化帧，但交互风险高，不建议动。
- **CheckImage 双分支检查**：CreateBmpTexture 不置 TextureValid 导致每图首次访问走双分支，但第二次即建 DX 纹理短路，无重复开销，健康。
- **GetTilesPreview 开头 288x192 位图在部分分支被丢弃重建**：轻微浪费，低收益不改动。
- **GetTilesPreview 4 处 `Images[index]=null` 用共享字段清错库**：上游缺陷（清错图→重复 CheckImage），已多次记录，涉及绘制正确性语义，单独评估。
