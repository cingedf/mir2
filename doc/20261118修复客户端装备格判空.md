# 20261118修复客户端装备格判空

## 现象

子代理残余 bug 审计发现：客户端 `EquipSlotItem`（装备结果处理）是同类处理器中**唯一**把目标格/来源格判空注释掉的，服务端下发的格子若在当前 UI 中找不到（对应窗口未打开/格子索引失效），会触发空引用异常。

## 排查过程

- 读 `Client\MirScenes\GameScene.cs:2615-2669` 现场：`EquipSlotItem` 在 switch 里取 `toCell`（按装备槽）与 `fromCell`（按 Inventory/Storage），:2634 判空被注释（`//if (toCell == null || fromCell == null) return;`），随后 :2636-2637 直接 `toCell.Locked = false; fromCell.Locked = false;`。
- 对照紧邻的 `CombineItem`（:2663）：`if (toCell == null || fromCell == null) return;` 是标准先例——同类处理器都先判空再访问格子。
- 根因：装备操作由服务端 `S.EquipSlotItem` 包驱动，若客户端对应窗口（如仓库/护身符栏）此刻未打开，`GetCell` 返回 null，注释掉判空后直接 NRE，可能中断该次包处理链。

## 修复内容

`Client\MirScenes\GameScene.cs`（EquipSlotItem :2634）：恢复判空 `if (toCell == null || fromCell == null) return;`（附 20261118 注释，说明对照 CombineItem 先例）。恢复后：格子找不到时安静 return，不影响后续合法装备结果处理。

## 验证证据

- `dotnet build Client\Client.csproj -c Release -p:ApplicationIcon=`：**0 错误**（1 存量 MSB3277 警告）；
- 行为复核：合法装备结果（to/from 格均存在）路径完全不变；仅格缺失时由 NRE 改为提前 return。
