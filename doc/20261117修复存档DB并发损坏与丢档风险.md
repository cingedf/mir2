# 20261117修复存档DB并发损坏与丢档风险

## 现象

第五轮深度审计（存档/数据库层）回报 3 项 P0 数据丢失风险和 1 项 P1 恢复缺陷：

1. **P0-1 账号档搬空 + 无异常保护**（Envir.cs:1464-1488 BeginSaveAccounts）：`File.Move(AccountPath, backupFile)` 把活档整个搬走；从此处到 EndSaveAccounts 替换前，账号主档始终不存在。若 SaveAccounts/FileStream/BeginWrite 任一抛异常（无 try/finally），活档只剩 .bak，且 `Saving` 永久停在 true → 关服时 `SaveAccounts()` 的 `while(Saving)Thread.Sleep(1)` **死锁**。
2. **P0-2 好友列表计数不匹配坏档**（CharacterInfo.cs:583-588 Save vs :336-340 Load）：`writer.Write(Friends.Count)` 写 N，但循环内 `if (Friends[i].Info == null) continue;` 跳过删档好友，实际写入 < N 条；Load 按 N 条读 → 流错位 → **服务器启动崩溃**。
3. **P0-3 MirDB 并发写损坏**（Envir.cs:1127-1195 SaveDB）：全仓调用面 = 主线程 WorkLoop 周期存 + **18 处 Server.MirForms UI 按钮** + tools 多处；原实现无锁且直接 `File.Create(DatabasePath)` 写活档，UI 线程与主循环并发调用时两线程互相截断 → **MirDB 损坏**；写入中途异常同样损坏活档。
4. **P1 异步替换失败无恢复**（Envir.cs:1490-1515 EndSaveAccounts）：旧档已被 Move 成 `+"o"`，异步替换异常时活档可能缺失却无回滚。

## 排查过程

- BeginSaveAccounts 全流程逐行读：确认搬档舞步（:1479 Move → :1483 `AccountPath+"n"` → BeginWrite → EndSaveAccounts :1503 Move 回主档）中间窗口主档缺失；EndSaveAccounts 已有的替换舞步（旧档→`+"o"`、新档→旧档、删 `+"o"`）本身就能处理旧档存在的情况，故 :1479 的 Move 纯属多余且危险。
- FriendInfo.Info getter（CharacterInfo.cs:793-803）为延迟 `Envir.GetCharacterInfo(Index)` 查找；好友删档后返回 null，但 Index/Blocked/Memo（:790/:806/:807）仍有效，FriendInfo.Save（:823-828）只写这三字段、不解析 Info——跳过毫无必要且有害。
- SaveDB 调用面全仓 grep 确认（GameShop/ItemInfoForm/MagicInfoForm 等 18 处 UI 按钮 + WorkLoop + LoadDB），`LoadLock`（Envir.cs:110）已用于 LoadDB/LoadCharacters，可复用（C# lock 可重入，LoadDB 内调 SaveDB 不死锁）。
- MessageQueue.Enqueue(ex) 直收 Exception 是既有惯例（EndSaveConquestsAsync:1460、EndSaveAccounts:1511）。

## 修复内容

**Envir.cs：**
1. **BeginSaveAccounts**：:1479 `File.Move(AccountPath, backupFile)` → `File.Copy(...)`（活档永不离开原位；同名旧备份在 :1478 已先删，Copy 安全）；整个方法体包 `try/catch`，异常时 `MessageQueue.Enqueue(ex); Saving = false;`（防关服死锁）。
2. **EndSaveAccounts catch**：补恢复逻辑——先 `fStream.Dispose()`（EndWrite 失败时可能未释放句柄），若活档不存在且 `+"o"` 存在则 `File.Move(oldfilename+"o", oldfilename)` 回滚；二次异常独立 catch 记录。
3. **SaveDB**：整体包 `lock (LoadLock)` 消除 UI/主循环并发；改原子写——先完整写 `DatabasePath+"n"` 临时文件，再执行替换舞步（旧档→`+"o"` → 临时档→活档 → 删 `+"o"`）；整体 `try/catch` + 失败时从 `+"o"` 恢复活档。备份 File.Copy 逻辑保留在锁内。

**CharacterInfo.cs：**
4. 删除好友 Save 循环内的 `if (Friends[i].Info == null) continue;`，始终写全部记录（count 自然对齐，同时消除存档期延迟 DB 查找副作用）。

## 验证证据

- `dotnet build Server.MirForms\Server.csproj -c Release`：**0 警告 0 错误**；
- 逻辑复核：SaveDB 加 lock 后与 LoadDB(:1519)/LoadCharacters 同锁互斥，重入调用（LoadDB→SaveDB）安全；原子替换保证任意时刻活档为完整旧档或完整新档；好友 Save 写入条数 == Friends.Count 与 Load 对齐；
- 待实测：正常存盘/关服无卡顿无死锁；UI 改动数据库资料后主循环周期存不报错；重启后好友列表正常、MirDB 正常加载。
