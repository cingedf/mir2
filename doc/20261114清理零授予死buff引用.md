# 20261114清理零授予死buff引用

> 死接线审计⑥产出：麻痹状态（=309）、伤口加深（=306）两枚举授予途径为零。用户已授权 AI 完全自主决策拍板（20261114 协作决策规范），选「清理引用、保留枚举值」方案。

## 现象

- **麻痹状态**：BuffType 枚举成员（Shared\Enums.cs:1601）+ BuffInfo 注册 + BuffDialog 图标 case（96）三环存在，但全仓零 AddBuff/零 HasBuff——麻痹玩法已由毒系统 `PoisonType.Paralysis`（=32，行动锁 HumanObject 125-161/授予点 20+ 处/UI 图标 233）完整覆盖，此枚举是被取代的孤儿。
- **伤口加深**：同构残留——宿主怪物 NobleAssassin（马灵，AI=505）无类文件、无工厂 case，部署区数据已把马灵改配 AI=502（NobleWarrior 天尊系）且无刷怪点；客户端 MapObject 光效 case（用 NobleAssassin 怪图 544 起 6 帧）+ BuffDialog 图标 case（94）成为无主资源。
- 两项均属「注册即生效面」死内容：BuffInfo.Load 会为它们创建注册项，虽无实际影响，但会误导后续审计与开发（例如被误接 GM 白名单）。

## 排查过程

- 审计子代理全链取证：两枚举全仓引用各仅 3 处（枚举定义/服务端注册/客户端 case），零业务消费；部署区 3_怪物数据.csv/6_刷怪数据.csv 确认宿主怪物（尊者系/马灵）均未投放或已改道。
- **序列化风险评估（本方案关键依据）**：`BuffType : ushort` 以数值落盘——S.AddBuff/NewMagic 等 8 处 `ReadUInt16` 强转、CharacterInfo.Buffs 存档。**删除枚举中间成员会使后续 ~1400 个值整体移位**，导致旧存档 buff 错映射、发包错光效。故弃「删枚举成员」，改「保留枚举值 + 清引用」：
  - 服务端注册删除后，运行期 `MapObject.AddBuff` 的 `buff.Info == null` 防御（MapObject.cs:649-653）会拒绝任何来源的该类型 buff；
  - 角色存档若历史残留此类型 buff，CharacterInfo.Load 的 `Info == null` 防御清理（503-540，带日志自动删除）兜底。
- 客户端 MapObject 光效 case 与 BuffDialog 图标 case 属纯 UI 映射，删除后未注册 buff 本就不可能到达客户端。

## 修复内容

1. **`Server\MirDatabase\BuffInfo.cs`**：删除 `伤口加深`（84）与 `麻痹状态`（87）两行注册，留注释说明死因与枚举值保留原因。
2. **`Client\MirObjects\MapObject.cs`**：删除 `case BuffType.伤口加深:` 光效块（348-350），留注释。
3. **`Client\MirScenes\Dialogs\BuffDialog.cs`**：删除 `case BuffType.伤口加深:`（94）与 `case BuffType.麻痹状态:`（96）图标 case。
4. **枚举成员（Shared\Enums.cs:1598/1601）保留**，值 306/309 不动，防序列化移位（注释性说明记于本 doc）。
